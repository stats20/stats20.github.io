What is a low level language? Assembly v R

  • Assembly invented in 1947, R 1993, fyi: Python 1989
.model small
.stack 100h

.data
a dw 2
b dw 5

.code
main proc
    mov ax, @data
    mov ds, ax

    mov ax, a
    mov bx, b
    add ax, bx

    add al, 30h
    mov dl, al
    mov ah, 02h
    int 21h

    mov ah, 4Ch
    int 21h
main endp
end main
  • In R
a <- 2
b <- 5

a + b
  • Extra (binary, the OG), 2 and 5, represented, not added yet
0000000000000010
0000000000000101
  • And the representation for 7 may make sense to you
0000000000000111

For your consideration

  • In assembly, we must tell the computer every tiny step. Assembly required humans to think/communicate like machines.
  • In R, Python, and other modern languages, we write what we want in a compact and more natural form
  • Programming languages evolved to let humans think less about machine details and more about ideas, data, and problems.
  • LLMs are part of the same long arc of evolution. They allow us to express intent in ordinary language. So “please add 2 and 5” as in the previous slide
  • Assembly -> C -> Python -> LLMs(?) older languages were not completely replaced – but their application may be narrower

A final thought on this

  • If you ask an LLM (I asked ChatGPT) what languages it rests upon, perhaps this answer is not too surprising:
Human language
   ↓
Python (or similar high-level language)
   ↓
C / C++ (fast execution)
   ↓
Assembly
   ↓
Machine code (binary)
  • it relies on many different tools for many different applications

What is NA in R?

  • NA represents unknown or unavailable data
  • It is NOT positive
  • It is NOT negative
  • It is not zero
  • not a number at all

There should be a value here, but we don’t know what it is.

What does NA mean to R?

5 + NA # NA
[1] NA
NA == 5 # NA
[1] NA
NA == NA # NA
[1] NA
is.na(NA) # TRUE
[1] TRUE
  • By not substituting a value, R lets the user decide how to address NA

What is JSON?

  • JSON stands for JavaScript Object Notation
  • JSON is a data-interchange format
  • JSON is language independent text so it can be used by different software
  • JSON is “human readable” and easy to understand
  • JSON structure is (or can be) hierarchical (values within values)
  • JSON is short and easy to write
  • JSON syntax is a subset of the JavaScript syntax.
  • The file type for JSON files is “.json”

  • SF Film Locations
library(httr)  # need this to get the URL
library(jsonlite) # need this to convert the json to a data frame

url_sf <- "https://data.sfgov.org/resource/yitu-d5am.json"

# first, make sure the URL is valid
check <- GET(url_sf, verbose())
status_code(check) # should return 200
[1] 200
# we see there are limits imposed, only 1000
locations_check <- fromJSON(content(check, "text"), flatten = TRUE)

Interpretation

  • GET() sends an HTTP request
  • We receive a response object with status code (200 - understood, 404 - not found, etc.) headers and content (the JSON)
  • fromJSON() converts the response to a data frame
  • They store the larger data, we access it in a legal orderly fashion.

Takeaways

  • Rectangular format of csv, tsv, txt, Excel is older
  • There are even older forms of data that are seen in specific disciplines
  • JSON is transitional and is used in many places
  • Newer formats (e.g., parquet, arrow, etc.) exist for size & speed and for non-rectangular forms (later)
  • But data is just data, don’t let the different formats scare/stop you
