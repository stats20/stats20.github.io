A note on R objects and their names

This section was taken from “Advanced R” by Hadley Wickham (chief scientist at Posit, the creators of RStudio). Only the most essential part was taken from his book on this subject. While I use the word “gets” in a first Stats 20 lecture to help make it more accessible, technically, that day one explanation of the “<-” isn’t quite accurate and if you plan to do any advanced R programming in the future, it is best to make it as clear as possible from the begining. My notes and comments are in a different color - magenta

from Chapter 2.2 “Binding Basics”

Consider this code:

x <- c(1, 2, 3)

It’s easy to read it as: “create an object named ‘x’, containing the values 1, 2, and 3”. ( or R object ‘x’ gets the vector 1, 2, 3 ) Unfortunately, that’s a simplification that will lead to inaccurate predictions about what R is actually doing behind the scenes. It’s more accurate to say that this code is doing two things:

  • It’s creating an object, a vector of values, c(1, 2, 3).
  • And it’s binding (associating) that object to a name, x.

In other words, the object, or value, (technically) doesn’t have a name; it’s actually the name x here that has a value 1, 2, 3.

To further clarify this distinction, I’ll draw diagrams like this:

The name, x, is drawn with a rounded rectangle. It has an arrow that points to (or binds or references) the value, the vector c(1, 2, 3). The arrow points in opposite direction to the assignment arrow: <- creates a binding from the name on the left-hand side to the object on the right-hand side.

Thus, you can think of a name as a reference to a value. For example, if you run this code, you don’t get another copy of the value c(1, 2, 3), you get another binding to the existing object:

y <- x

You might have noticed that the value c(1, 2, 3) has a label: 0x74b. While the vector doesn’t have a name, I’ll occasionally need to refer to an object independent of its bindings. To make that possible, I’ll label values with a unique identifier. These identifiers have a special form that looks like the object’s memory “address”, i.e. the location in memory where the object is stored. But because the actual memory addresses changes every time the code is run, we use these identifiers instead.

You can access an object’s identifier with lobstr::obj_addr(). Doing so allows you to see that both x and y point to the same identifier:

obj_addr(x)
[1] "0x14258d6c8"
obj_addr(y)
[1] "0x14258d6c8"

These identifiers are long, and change every time you restart R.

It can take some time to get your head around the distinction between names and values, but understanding this is really helpful in functional programming where functions can have different names in different contexts.

(end Wickham)

The result of R’s ways

So take a look at what happens when we modify one but not the other

y[[3]] <- 4   ## I am following Wickham's style here, 

## instead you could have used y[3] <- 4 
## read as "y's third element" gets 4
## because we have simple vector, in other places 
## y[[3]] <- 4 is clearer, but we're not there yet

x
[1] 1 2 3
y
[1] 1 2 4

let’s check the memory locations

obj_addr(x)
[1] "0x14258d6c8"
obj_addr(y)
[1] "0x114e06f78"

(start Wickham again)

Modifying y clearly didn’t modify x. So what happened to the shared binding? While the value associated with y changed, the original object did not. Instead, R created a new object, 0xcd2, a copy of 0x74b with one value changed, then rebound y to that object.

This behaviour is called copy-on-modify. Understanding it will radically improve your intuition about the performance of R code.

(end Wickham)

Do you need to completely understand this to do well in Stats 20? Probably not BUT if you decide to learn Python or become a paid R programmer later (because all of the documentation assumes you understand R’s decision making in memory), it would help to understand what he is trying to tell you in Chapter 2 of the textbook Advanced R.
